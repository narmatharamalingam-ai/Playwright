# Test Plan — SauceDemo UI Automation

| | |
|---|---|
| **Application under test** | https://www.saucedemo.com/ |
| **Framework** | Playwright Test (`@playwright/test` 1.62.1), JavaScript / CommonJS |
| **Pattern** | Page Object Model with a `POManager` factory |
| **Design** | Data-driven (JSON datasets) + a custom fixture (`Utils/test-base.js`) |
| **Suite size** | 11 assignment tests + 2 scaffolding tests = 13 collected |
| **How to run** | see [execution.md](execution.md) |

---

## 1. Objective

Validate the core customer journey of the SauceDemo storefront — authentication,
product browsing, cart management and checkout — and confirm that the site's
deliberately seeded per-user defects (locked-out, broken images, glitched
performance, failing add-to-cart) behave as documented.

## 2. Scope

### In scope
- Login for all six seeded personas
- Inventory listing: item, price and action button rendering
- Product image integrity per persona
- Add to cart, add multiple, remove from inventory page and from cart page
- Cart badge counting
- Checkout: personal information form, overview, completion, cancel
- Price consistency from inventory to cart to checkout overview
- Logout

## 3. Test approach

| Layer | Responsibility |
|---|---|
| `tests/Waracletest.spec.js` | orchestration only — arranges the journey, no locators |
| `pageObjects/*.js` | locators and page actions |
| `pageObjects/POManager.js` | single construction point for all page objects |
| `Utils/*.json` | login and end-to-end datasets |
| `Utils/test-base.js` | `testdataforbrowse` fixture for the cart/checkout tests |

Login and end-to-end cases are generated by looping over a JSON array, so a new
persona is added by appending one object — no new test code.


## 5. Test data

All personas use password `secret_sauce` (the site publishes these credentials on
its own login page, so they are not secrets).

| Persona | Source file | Expected behaviour |
|---|---|---|
| `standard_user` | `testdata.json`, `endtoendtestdata.json`, fixture | fully working baseline |
| `locked_out_user` | `testdata.json` | login rejected with error banner |
| `problem_user` | `testdata.json` | all product images identical |
| `visual_user` | `testdata.json` | one product image swapped / broken |
| `performance_glitch_user` | `endtoendtestdata.json` | works, but slow to load |
| `error_user` | `endtoendtestdata.json` | add-to-cart silently fails |

## 6. Test cases

Legend for **Status**: **Full** = automated and meaningfully asserted;
**Partial** = automated but the assertion is weak or incomplete;
**No assert** = the action runs but the outcome is never verified.

### TC01 — Login: `standard_user`
**Steps:** navigate to base URL, fill username, fill password, click Login.
**Expected:** URL becomes `/inventory.html`; inventory renders.
**Status:** Partial — the URL is asserted; the inventory-loaded check is skipped for this persona (see section 9, D3).

### TC02 — Login: `locked_out_user`
**Steps:** navigate, fill credentials, click Login.
**Expected:** the error container is visible and contains `Epic sadface: Sorry, this user has been locked out.`; the app does **not** navigate to `/inventory.html`.
**Status:** Full.

### TC03 — Login: `problem_user`
**Steps:** log in, read the `src` of every inventory image.
**Expected:** inventory items, prices and Add-to-cart buttons render; **all** image sources collapse to a single unique value (the seeded defect).
**Status:** Partial — the image-duplication assertion is real and correct; the item/price/button render check is a no-op (see section 9, D2).

### TC04 — Login: `visual_user`
**Steps:** log in, read the `src` of every inventory image.
**Expected:** every image source is distinct, **and** at least one source contains `sl-404` (the seeded broken image).
**Status:** Partial — image assertions are real; the render check is the same no-op as TC03.

### TC05 — End-to-end purchase: `standard_user`
**Steps:** log in; capture the price of *Sauce Labs Onesie* and add it to the cart; assert badge = 1; open the cart; assert the cart price matches the captured price; Checkout; fill first name / last name / postcode; Continue; assert product name and price on the overview; Finish; assert completion; log out.
**Expected:** the captured price survives unchanged through cart and overview; `Checkout: Complete!` and `Thank you for your order!` are shown; logout returns to the login URL.
**Status:** Full for name, price and completion. Subtotal, tax and total are **not** asserted (see section 9, gap G1).

### TC06 — End-to-end purchase: `performance_glitch_user`
Identical to TC05 with *Sauce Labs Bike Light*. Also exercises the suite's tolerance of the persona's artificial latency.
**Expected:** same as TC05; no timeout despite the delay.
**Status:** Full (same subtotal/tax/total gap as TC05).

### TC07 — Negative end-to-end: `error_user`
**Steps:** log in, click Add to cart for *Sauce Labs Bolt T-Shirt*.
**Expected:** the cart badge never appears — the seeded add-to-cart failure.
**Status:** Partial — `toBeHidden()` also passes when the element is absent for *any* reason, so the assertion does not distinguish "add failed" from "page broke". Asserting that the button label stayed `Add to cart` would be stronger.

### TC08 — Browse products and add to cart
**Steps:** log in as `standard_user`, add *Sauce Labs Onesie*.
**Expected:** badge = 1.
**Status:** Partial — the add-to-cart half is asserted, but no browsing is actually performed. The sort dropdown locator (`product_sort_container`) is declared but never exercised (see section 9, gap G2).

### TC09 — Add two items, remove one
**Steps:** log in; add *Sauce Labs Onesie* (assert badge = 1); add *Sauce Labs Fleece Jacket* (assert badge = 2); click Remove on the first item.
**Expected:** the badge decrements to 1.
**Status:** Full — the strongest of the standalone cases.

### TC10 — Remove an item from the cart page
**Steps:** log in, add an item, open the cart, click Remove.
**Expected:** the row disappears and the badge clears.
**Status:** No assert — the click happens, but nothing after it is verified (see section 9, D4).

### TC11 — Cancel from the personal-information page
**Steps:** log in, add an item, open the cart, Checkout, fill the form, click Cancel.
**Expected:** the user returns to the cart page with the item still present.
**Status:** No assert — same issue as TC10.

## 8. Entry and exit criteria

**Entry:** dependencies installed (`npm ci`), browsers installed, saucedemo.com reachable.

**Exit:** all assignment tests green; no test in the suite passes without at least one meaningful assertion; HTML report and traces published as CI artifacts.
